# 지원자-공고 매칭 스코어링 엔진

채용공고 이미지에서 지원 조건을 추출하고, 지원자의 이력서와 비교해 0~100점으로 순위를 매기는 엔진입니다.
점수만 보여주지 않고 조건별 판정과 근거 문장도 함께 제공합니다.

과제의 범위는 ‘인재풀 전체에서 사람을 추천하는 것’이 아니라, **특정 공고에 지원한 사람 중 누구를 먼저
검토할지 정하는 것**으로 잡았습니다. 채용 담당자가 결과를 이해하고 검산할 수 있도록 LLM은 조건 충족 여부만
판정하고, 최종 점수는 코드가 계산합니다.

## 동작 방식

핵심 원칙은 숫자로 확인할 수 있는 조건은 코드로 비교하고, 표현의 의미(맥락)를 읽어야 하는 조건에만
임베딩과 LLM을 사용합니다.

```
공고 이미지 ─ 분할 ─ 비전 LLM 구조화 ─ OCR 교차검증 ─→ JobPosting JSON
                                                          │
이력서 ─ 문장·절 분리 ───────────────────────────────────→ 조건별 판정
                                                          │  ├ 연차 조건  → 코드 비교
                                                          │  ├ 나머지     → 임베딩 유사도
                                                          │  └ 애매한 것  → LLM 재판정
                                                          ▼
                                            점수 계산(코드) → 랭킹 + 근거
```

LLM에 점수를 직접 물으면 같은 입력에도 결과가 달라질 수 있고, 정책 변경이나 결과 재현도 어렵습니다.
그래서 LLM에는 “이 조건을 충족하는가?”와 “근거 문장은 무엇인가?”만 묻습니다.

## 빠르게 실행하기

```bash
uv sync
cp .env.example .env  # .env에 OPENAI_API_KEY 입력
uv run uvicorn app.api.main:app --reload
```

실행 후 UI는 `http://localhost:8000`, 매칭 API는 `/jobs/{job_id}/matches`에서 확인할 수 있습니다.

```bash
uv run pytest  # 51개 테스트, OpenAI 호출 없음
```

공고 이미지 파싱 방법, 품질 채점과 분석 도구 사용법은 [NOTES.md](NOTES.md)에 따로 정리했습니다.

## 주요 설계 결정

### 1. 조건에 맞는 판정기를 선택한다

`min_years`가 있는 조건은 코드로 숫자를 비교합니다. 이를 임베딩에 맡기면 이력서에 “경력 3년 이상”이라는
문구만 있어도 실제 경력과 관계없이 충족으로 볼 수 있기 때문입니다. 나머지 조건은 임베딩으로 먼저 판정하고,
충족 여부를 확정하지 못한 조건만 이력서 전문과 함께 LLM에 다시 묻습니다.

- **효과:** “화장품 단상자 그래픽 설계, 인쇄소 입회 색 교정”과 “패키지 디자인 및 감리 경험”처럼
  표현은 다르지만 의미가 같은 경험을 찾을 수 있습니다.
- **복잡도:** 판정 경로가 세 가지로 늘어납니다. 대신 결과에 `judged_by`를 남겨 어떤 방식으로 판정했는지
  화면에서 확인할 수 있게 했습니다.
- **비용:** 여러 조건을 한 요청으로 묶어 LLM은 지원자 한 명당 한 번만 호출합니다. 조건이 늘어도 호출
  횟수는 그대로이고, 같은 (조건, 이력서) 조합은 캐시해 다시 묻지 않습니다.

처음에는 유사도가 0.35~0.65인 조건만 LLM에 보냈습니다. 하지만 “생산팀, 품질팀과 논의하며 사양을 확정”한
경험이 “유관 부서와 원활한 커뮤니케이션” 조건에서 0.28을 받아 미충족으로 남았습니다. 하한을 낮춰도 경계만
옮겨갈 뿐이어서, 지금은 임베딩이 충족으로 확정하지 못한 조건을 모두 재판정합니다. 그 결과 잘못된 미충족
2건을 고쳤고, 미스매칭 지원자의 점수는 그대로 유지됐습니다.

### 2. 임계값은 라벨 데이터로 정한다

처음에는 임계값을 0.75/0.55로 잡았지만, 완벽 매칭으로 설계한 지원자가 23.1점을 받았습니다. 목업 이력서에
완벽/부분/미스매칭 라벨을 붙인 뒤, 라벨의 순서가 뒤집힌 횟수로 임계값 조합을 비교했습니다.

```bash
uv run python -m tools.evaluate --sweep    # 임계값 조합 비교 + 안정 구간
```

| 임베딩 판정만 (임계값 조정에 쓴 공고 2건, 12명) | 순위 역전 |
|---|---|
| 0.75 / 0.55 (초기 추측) | 3회 |
| **0.70 / 0.30 (채택)** | **1회** |

특정 값 하나에만 맞춘 결과인지도 확인했습니다. met `0.70~0.75` × partial `0.30`의 두 조합이 같은 결과이고,
partial을 0.35로 올리면 역전이 늘어납니다. 안정 구간이 met 방향으로만 넓다는 뜻입니다.

LLM 재판정을 켜면 확인한 조합 중 met이 0.70 이하일 때는 역전이 0회, 0.75일 때는 1회였습니다. 임계값이
결과를 가르는 건 LLM을 쓸 수 없을 때이므로, 그 상황에서 남는 품질을 기준으로 골랐습니다.

### 3. 한국어 이력서는 절 단위로 나눈다

> "시각디자인을 **전공하고** 화장품 브랜드사에서 7년간 제품 패키지 디자인을 담당했습니다."

문장 전체를 “디자인 관련 전공이신 분”과 비교하면 유사도는 0.28이었습니다. 전공 정보가 다른 경력 내용에
묻혔기 때문입니다. 쉼표와 연결어미(`~하고`, `~며`, `~면서`, `~지만`, `~는데`, `~해서`)를 기준으로 나누자
유사도가 0.48로 올랐습니다.

대신 청크가 늘어 임베딩 호출이 많아지고, “신고”나 “브랜드사에서” 같은 단어를 연결어미로 잘못 자르지 않도록
예외 처리가 필요했습니다. 또 이 규칙은 직군에는 무관하지만 한국어에 종속됩니다. 형태소 분석기는 더 정확하지만
의존성이 무겁고, 고정 길이 윈도우나 LLM 청킹은 각각 근거 문장의 품질과 비용 문제가 있습니다. 현재 청킹은
임베딩 판정과 근거 문장 표시에만 쓰고, 확정하지 못한 조건은 LLM이 이력서 전문을 읽도록 했습니다.

### 4. 필수 조건을 놓치면 점수에 상한을 둔다

가중치만으로는 (필수 1개 누락 + 우대 전부) 80점이 (필수 전부 + 우대 1개) 70점을 이깁니다.
탈락 처리는 판정이 틀렸을 때 사람을 잃고, 필수 가중치를 키우는 것은 여전히 덧셈이라 크게 달라지지 않습니다.
그래서 **점수와 순서는 남기되 상한을 두는** 방식을 골랐습니다.

처음 구현(필수 1개라도 미충족이면 상한 40)은 실패했습니다. 6명 중 4명이 정확히 40.0점으로 뭉쳐 변별이 사라졌습니다.
그래서 개수가 아니라 비율로 봅니다. 필수 조건을 충족 1점, 부분 충족 0.5점, 미충족 0점으로 세어 필수 조건 수로
나눈 값이 **필수 충족률**이고, 이 값이 0.8 미만이면 70점, 0.5 미만이면 40점으로 상한을 둡니다. 필수 5개 중
3개 충족, 1개 부분 충족이면 충족률은 0.7이라 원점수가 85점이어도 70점이 됩니다.

개수로 세면 필수가 14개인 공고에서 1개를 놓친 지원자와 5개 중 1개를 놓친 지원자가 똑같이 "1개 누락"이 됩니다.
비율로 보면 각각 0.93과 0.8이라 조건 수가 다른 공고를 같은 기준으로 비교할 수 있습니다.

남은 한계는 모든 필수 조건을 같은 무게로 본다는 점입니다. 필수 조건 사이의 중요도 차이는 공고 원문만으로
판단할 수 없어, 고객사에게 직접 입력받는 구조로 확장할 지점으로 뒀습니다.

### 5. LLM이 만든 결과는 원문과 대조한다

LLM은 원문에 없는 내용을 만들 수 있으므로 공고 파싱과 조건 판정, 두 단계에서 결과를 검증합니다.

- **공고 파싱:** 비전 LLM이 뽑은 조건이 OCR 원문에 있는지 확인합니다. **확인되지 않은 조건은 조용히 버리지
  않고 목록으로 보여준 뒤 기본 제외**하며, 실행하는 사람이 원본을 보고 `--include {조건 id}`로 포함시킵니다.
  웹 개발자 공고에서 2건이 걸렸는데 OCR이 "Next.js"를 `46×[.15`로, "사용"을 `AAS`로 잘못 읽은 경우였습니다
  (`uv run python -m app.parsing.cli barog-developer --dry-run`으로 재현됩니다).
- **조건 판정:** LLM이 인용한 근거 문장이 이력서 원문에 있는지 확인합니다. 없으면 근거를 버리고 사유에 남깁니다.

이 방식은 원문에 아예 없는 내용은 걸러내지만, 원문의 단어를 재조합한 문장에는 약합니다. "유관 부서와 원활한
커뮤니케이션이 가능하신 분"에서 단어만 바꾼 "영어 커뮤니케이션이 가능하신 분"은 원문과 충분히 비슷해 그대로
통과할 수 있습니다. 그래서 검증을 통과한 조건도 최종 확인은 사람이 하는 흐름으로 뒀습니다.

실제 공고 세 건에서는 파싱 오류가 없었고, 미검증으로 걸린 두 건은 모두 OCR 오인식이었습니다. OCR은 조건
추출이 아니라 검증 보조 수단이고, 실패한 항목은 사람이 확인할 수 있어 가벼운 Tesseract를 사용했습니다.
제품에서는 이 과정을 공고 등록 화면에 넣습니다. 검증을 통과한 조건은 자동 등록하고, 확신하지 못한 항목만 확인을 요청하는 방식입니다.

### 6. 새 직군은 코드 수정 없이 추가한다

직군 확장은 두 가지 기준으로 설계했습니다.

- **새 직군이 들어와도 코드를 고치지 않는다.** 코드에는 스킬명이나 직군명을 넣지 않았습니다. 비전 LLM
  프롬프트도 필수/우대 구분, 카테고리, 숫자로 명시된 경력 연수 같은 형식만 다룹니다. 패키지 디자이너,
  일본 이커머스 MD, 웹 개발자 세 직군으로 검증했습니다.
- **직군별 정확도는 데이터로 보완한다.** 직군마다 “BX”, “감리”, “라쿠텐 이치바”, “SSR”처럼 고유한
  표현이 있습니다. 이런 지식은 코드가 아니라 주입 가능한 용어 사전으로 관리합니다.

#### 적용한 방법: 직군별 용어 사전

`data/lexicon/*.json`에 `"Next.js" → ["리액트 기반 SSR 프레임워크"]` 같은 쌍을 두면, 조건 문장을 대체 표현으로
바꾼 문장까지 함께 비교하고 그중 가장 높은 유사도를 씁니다. 코드는 그대로 두고 파일만 추가하면 되며, 사전이
없어도 동작은 달라지지 않습니다. 임베딩으로 판정한 조건은 어떤 용어가 적용됐는지 사유에 남습니다(LLM이 다시
판정하면 사유는 LLM의 설명으로 바뀝니다).

| 임베딩 판정만, 임계값 0.70/0.30 (12명) | 순위 역전 |
|---|---|
| 용어 사전 없음 | 2회 |
| **용어 사전 적용 (채택)** | **1회** |

#### 제외한 방법: 키워드가 일치하면 바로 확정

고유 용어가 이력서에 그대로 있으면 유사도 비교 없이 충족으로 확정하는 판정기도 시험했습니다.
`전산회계 1급`과 `전산세무 2급`처럼 임베딩 공간에서는 가깝지만 실제로는 다른 자격을 구분하려는
의도였습니다. 하지만 순위 역전이 오히려 늘어 되돌렸고, 해당 코드는 남기지 않았습니다.

조건 문장은 단어 목록이 아니어서 키워드 규칙만으로 판단하기 어려웠습니다.
"React / Next.js 기반 프론트엔드 개발 경험"은 이력서에 "React"만 있어도 확정돼 버리고, 전부 요구하면
`A / B`처럼 둘 중 하나면 되는 나열을 모두 필수로 읽습니다. 실제 요구사항은 “기반 프론트엔드 개발 경험”이라는
문장 전체의 맥락에 있습니다.

이 밖에도 다음과 같은 확장 지점을 생각했습니다. 모두 구현하지는 않았습니다.

- **카테고리별 판정기 등록:** 어학은 등급 비교, 근무지는 좌표 거리 계산이 유사도보다 정확합니다.
  판정기가 프로토콜로 분리돼 있어 구현체를 추가하고 `service.py`의 라우팅만 고치면 되지만, 위 실험처럼
  **붙이기 전에 측정이 필요합니다.**
- **정책 계층화:** 직군과 고객사에 따라 중요하게 보는 능력이 다릅니다. 지금은 `scoring.yaml` 한 장이지만
  `기본값 → 직군별 → 고객사별`로 덮어쓰게 하면, 개발 직군은 스킬 가중치를 올리고 영업 직군은 경력을
  올리는 조정을 코드 수정 없이 할 수 있습니다.
- **구조화된 프로필 활용:** 실제 인재풀에서는 학력과 자격증이 별도 필드로 관리될 수 있습니다. 그러면
  `education` 같은 조건은 학력 필드와만 대조해 "전공이 안 맞음"과 "정보가 아예 없음"을 구분할 수 있습니다.
  이번 과제에서는 입력 조건을 유리하게 만들지 않기 위해 자유 텍스트만 사용했습니다.
- **피드백 루프:** 현재 화면은 판정 결과와 근거를 보여주는 데까지 구현했습니다. 앞으로 채용 담당자가
  조건별 판정을 수정할 수 있게 하고, 그 기록을 라벨 데이터로 쌓을 수 있습니다. 데이터가 충분히 모이면
  임계값과 프롬프트를 다시 조정하고, 변경 전후의 품질도 비교할 수 있습니다. 별도의 사전을 계속 손으로
  관리하기보다 실제 채용 과정에서 생기는 피드백으로 정확도를 높이는 방향입니다.

## 어떻게 검증했나

테스트는 커버리지 숫자를 높이기보다, 잘못돼도 겉으로 드러나지 않는 경우를 중심으로 51개를 작성했습니다.

- 우대 조건 점수가 필수 조건 누락을 덮어 순위가 뒤집히는가
- 경력 7년 같은 경계값이 부동소수점 오차로 미달 처리되는가
- 가장 유사한 문장을 근거로 고르는가
- LLM이 원문에 없는 근거를 만들었을 때 걸러지는가

테스트가 통과만 하는 장식이 아닌지 확인하려고, 해당 로직에 일부러 버그를 넣어 실제로 실패하는지도 봤습니다.

임계값을 조정한 데이터로만 평가하면 과적합을 알 수 없습니다. 그래서 세 번째 공고인 웹 개발자 공고와
이력서 6명은 임계값 조정에 사용하지 않고 검증용으로 남겼습니다.

```bash
uv run python -m tools.evaluate            # 전체 채점
uv run python -m tools.evaluate --holdout  # 검증용 공고만
```

| | 공고 | 지원자 | 순위 역전 |
|---|---|---|---|
| 임계값 튜닝용 | 디자이너, 일본 이커머스 | 12명 | **0회** |
| 검증용 (임계값 조정 안 함) | 웹 개발자 | 6명 | **0회** |

## 데이터 수집과 처리 경계 (설계)

공고와 인재 정보는 출처가 다릅니다. 인재풀은 서비스가 직접 보유하지만, 공고는 외부 채용 플랫폼에 있을 수
있습니다. 제품에서는 외부 플랫폼을 직접 크롤링하지 않고, 고객사가 자사 공고를 업로드하거나 ATS를 연동하는
구조를 가정했습니다.

```
[외부 채용 플랫폼]
      │ ① 고객사(채용 기업)가 자사 공고를 직접 확보 — 플랫폼과 고객사 사이의 계약 관계
      ▼
[고객사]  ─ ② 자사 공고 + 조건별 중요도를 업로드 (우리는 크롤링하지 않는다)
      │
      ▼
[매칭 엔진] ─ ③ 공고 조건 구조화 → 해당 공고 지원자들과 대조 → 랭킹 + 근거
      ▲
      │ 인재풀: 플랫폼이 직접 보유 (가입 시 지원자 동의)
[지원자]  ─ 공고에 지원
      ▼
[고객사에게 지원자 랭킹과 근거 제공]
```

- **공고:** 업로드 API와 ATS 연동을 제공합니다. 코드에서는 `JobImageSource` 인터페이스가 이 경계이며,
  현재의 로컬 폴더 구현을 고객사 업로드 구현으로 교체할 수 있습니다. 조건별 중요도도 이 경로로 받습니다.
- **자동화된 판단에 대한 설명:** 사람을 순위 매기는 처리라 "왜 이 사람이 상위인가"를 설명할 수 있어야 합니다.
  조건별 판정 사유와 근거 문장을 남기는 것은 품질 때문만이 아니라 이 요구 때문이기도 합니다.
  점수를 LLM에 맡기지 않은 이유도 같습니다.
- **보관:** 매칭 결과는 근거와 함께 보관하고 중간 산출물은 목적을 다하면 파기하는 기준이 필요합니다.
  현재 구현은 결과를 저장하지 않고 요청할 때마다 계산하며, 파일로 남는 것은 임베딩과 판정 캐시뿐입니다.

## 한계와 다음 단계

1. **연차는 총 경력으로만 비교합니다.** "일본 이커머스 MD 경력 3년"에 다른 직무 3년도 충족이 됩니다.
2. **LLM 재판정이 경계 사례에서 후합니다.** "라쿠텐 생활잡화 MD 4년"을 "브랜드 공식 라쿠텐 몰 운영" 충족으로
   봤습니다. 사람에 따라 갈릴 판단이라 프롬프트를 조이지 않고, 판정 사유를 화면에 노출해 검토할 수 있게 했습니다.
   다음 단계로는 담당자가 판정을 직접 수정하고 그 기록을 품질 개선에 쓰는 기능이 필요합니다.
3. **대규모 스카우트 추천에는 바로 적용하기 어렵습니다.** 지금 범위는 공고별 지원자가 수십~수백 명이라
   현재 구조로 충분합니다. 하지만 인재풀 전체에서 후보를 찾는 방식으로 넓히면 지원자마다 LLM을 호출하는
   비용이 커집니다. 그때는 **임베딩으로 후보를 좁힌 뒤 상위 후보만 LLM으로 판정하는 2단계 구조**가 필요합니다.
   중간에 조건 문장과 이력서 문장을 함께 입력받아 관련도를 매기는 크로스 인코더를 두면 LLM에 넘길 후보를
   더 줄일 수 있습니다.

## 과제를 하면서 든 생각

**필수 조건 n개가 정말 같은 무게일까.** 공고에는 필수 조건이 여러 개 나열되지만, 그중에는 못 채우면 곧
불합격인 조건과 다른 강점으로 양보할 수 있는 조건이 섞여 있다고 생각했습니다. "일본어 커뮤니케이션"은
못 하면 업무 자체가 어렵지만 "디자인 관련 전공"은 실무 능력으로 대체될 수 있습니다. 문제는 공고 원문만으로는
둘을 구분할 수 없다는 점입니다.  그래서 조건별 중요도는 시스템이
추측할 값이 아니라 공고를 올리는 고객사에게 입력받아야 하는 값이라고 판단했습니다.

**임베딩이 못 푸는 문제는 예전에 어떻게 풀었을까.** 단어는 다른데 맥락이 같아 사실상 같은 경험인 경우와,
반대로 단어는 같은데 뜻이 다른 경우를 임베딩은 자주 놓칩니다. 지금은 LLM 재판정이 그 자리를 메우고 있는데,
LLM이 없던 시절이라면 "A는 B와 관련이 있다" 같은 관계를 사람이 구조화해 쌓는 방식, 즉 온톨로지로 풀었을
것 같다는 생각이 들었습니다. 직군처럼 도메인을 좁혀 사전을 쌓으면 그 안에서는 더 깊게 추론할 수 있을테니 각 직군별로 더 믿을 수 있는 결과가 나올 수 있지 않을까 합니다.

LLM이 있는 지금은 그 사전을 사람이 규칙으로 관리하는 대신 LLM에게 판단 재료로 넘기면서 사전 관리까지 할 수 있다 생각됩니다.

## 프로젝트 구조

```
app/domain/models.py     도메인 모델 (정의되지 않은 필드는 거부)
app/ingest/source.py     공고 원본 입력 (로컬 폴더 → 이후 API/고객사 업로드)
app/parsing/             이미지 분할 → 비전 LLM → OCR → 교차 검증 → CLI
app/matching/            청킹, 임베딩, 판정기 3종, 점수 계산, 랭킹
app/api/main.py          FastAPI + UI 서빙
config/                  scoring.yaml(임계값·가중치·상한), parsing.yaml(비전 모델·OCR·검증 기준)
data/                    raw(공고 원본), jobs, resumes(목업 이력서), lexicon(용어 사전), expected(라벨), parsed(검증 리포트), cache
tools/                   evaluate.py(품질 채점), export_vectors.py(유사도 히트맵)
```
